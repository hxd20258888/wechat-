# 管理员邀请码与时段生成设计

## 1. 背景

当前项目已经具备服务展示、用户预约、我的预约、管理后台、服务管理、时段管理和预约管理等基础功能。但现有实现存在几个会影响上线安全和可用性的缺口：

- `bindAdmin` 可以无条件把当前用户提升为管理员。
- `manageTimeSlot` 前端调用了 `updateWeekly`，后端尚未实现。
- 创建预约时没有校验时段容量，也没有更新 `bookedCount`。
- 更新预约状态时没有校验用户归属或管理员权限，也没有同步释放时段容量。

本设计聚焦两个已确认需求：

- 用户在小程序中输入邀请码绑定管理员身份。
- 管理员保存每周固定时段后，系统自动生成未来 14 天的实际可预约时段。

## 2. 目标

1. 管理员绑定必须通过邀请码校验，不能开放提权。
2. 每周固定时段配置保存后，生成未来 14 天 `time_slots` 数据。
3. 时段生成过程必须幂等，重复保存不会生成重复时段。
4. 已有预约的时段不能被误删，避免影响客户预约记录。
5. 预约创建、取消、确认、完成等状态变化要保持时段容量一致。
6. 后端云函数必须承担最终权限和数据校验，不能只依赖前端。

## 3. 非目标

- 不引入新的后端服务，继续使用微信云开发云函数和云数据库。
- 不重做管理后台整体 UI，只在现有页面上补必要入口和状态反馈。
- 不实现复杂排班规则，例如多段营业时间、节假日模板、跨天时段。
- 不改变现有 `services`、`appointments`、`time_slots` 的核心集合命名。

## 4. 数据模型

### 4.1 admin_invites

管理员邀请码集合，用于控制谁可以绑定管理员。

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 云数据库文档 ID |
| `code` | string | 邀请码明文。初期可直接保存，后续可升级为 hash |
| `isActive` | boolean | 是否启用 |
| `expiresAt` | Date | 过期时间，可为空表示长期有效 |
| `maxUses` | number | 最大使用次数，可为空表示不限次数 |
| `usedCount` | number | 已使用次数 |
| `createdAt` | Date | 创建时间 |
| `updatedAt` | Date | 更新时间 |

初期为了实现简单，邀请码可以明文保存。后续如需提高安全性，可改为保存 `codeHash`，云函数对用户输入做 hash 后查询。

### 4.2 admin_invite_logs

邀请码使用日志，便于排查和审计。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `_id` | string | 云数据库文档 ID |
| `inviteId` | string | 对应 `admin_invites._id` |
| `_openid` | string | 使用邀请码的用户 openid |
| `usedAt` | Date | 使用时间 |
| `result` | string | `success` 或失败原因 |

### 4.3 time_slots

沿用现有集合，补充幂等和规则来源字段。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `date` | string | 日期，格式 `YYYY-MM-DD` |
| `startTime` | string | 开始时间，格式 `HH:mm` |
| `endTime` | string | 结束时间，格式 `HH:mm` |
| `maxCount` | number | 最大预约数 |
| `bookedCount` | number | 已预约数 |
| `isAvailable` | boolean | 是否开放预约 |
| `source` | string | `weekly` 或 `manual` |
| `weeklyDayOfWeek` | number | 来源星期，0-6 |
| `createTime` | Date | 创建时间 |
| `updateTime` | Date | 更新时间 |

建议业务唯一键为：

```text
date + startTime + endTime
```

微信云数据库没有强唯一索引时，云函数需要在写入前查询已存在记录并更新，避免重复新增。

## 5. 管理员邀请码绑定

### 5.1 前端流程

在“我的”页或管理入口附近增加“绑定管理员”入口：

1. 用户未登录时，先引导微信登录。
2. 用户点击“绑定管理员”。
3. 弹出输入框，输入邀请码。
4. 调用 `bindAdmin` 云函数，入参：

```json
{
  "inviteCode": "用户输入的邀请码"
}
```

5. 成功后刷新 `checkAdmin`，显示管理后台入口。
6. 失败时显示明确提示，例如邀请码无效、已过期、已达到使用次数。

### 5.2 后端流程

`bindAdmin` 必须改为受控提权：

1. 获取当前用户 `openid`。
2. 校验 `inviteCode` 非空。
3. 查询 `admin_invites` 中启用的邀请码。
4. 校验是否过期。
5. 校验是否超过 `maxUses`。
6. 查询或创建当前用户记录。
7. 将当前用户更新为 `isAdmin: true`。
8. 增加邀请码 `usedCount`。
9. 写入 `admin_invite_logs`。
10. 返回 `{ isAdmin: true }`。

用户已经是管理员时，可以直接返回成功，不重复消耗邀请码次数。

## 6. 每周固定时段生成

### 6.1 前端调用

现有 `adminTimeSlots` 页已经维护 `weeklyConfigs`，保存时继续调用：

```json
{
  "action": "updateWeekly",
  "configs": [
    {
      "dayOfWeek": 6,
      "label": "周六",
      "isActive": true,
      "startTime": "09:00",
      "endTime": "18:00",
      "maxCount": 1
    }
  ]
}
```

前端保存成功后，刷新当前日期的时段列表。

### 6.2 后端生成规则

`manageTimeSlot` 增加 `updateWeekly` 分支：

1. 校验管理员权限。
2. 校验 `configs` 为数组。
3. 生成从今天开始未来 14 天的日期列表。
4. 对每一天根据 `date.getDay()` 匹配对应 `weeklyConfigs.dayOfWeek`。
5. 对 `isActive: true` 的配置生成或更新具体 `time_slots`。
6. 对 `isActive: false` 的未来空时段进行关闭处理。

### 6.3 幂等策略

对每个待生成时段，先查询：

```text
date = 当前日期
startTime = 配置开始时间
endTime = 配置结束时间
```

如果不存在：

- 新增 `time_slots`。
- `bookedCount` 初始化为 `0`。
- `isAvailable` 为 `true`。
- `source` 为 `weekly`。

如果已存在：

- 更新 `maxCount`、`isAvailable`、`source`、`weeklyDayOfWeek`、`updateTime`。
- 保留原有 `bookedCount`。
- 如果 `bookedCount > maxCount`，不强行降低已预约数量，只让前端显示已满。

### 6.4 关闭规则

当某个星期配置从启用改为停用时：

- 对未来 14 天内 `source = weekly` 且匹配该星期的时段进行处理。
- 如果 `bookedCount > 0`，只设置 `isAvailable: false`，保留记录。
- 如果 `bookedCount = 0`，建议也先设置 `isAvailable: false`，不删除记录。

选择关闭而不是删除，可以保留审计和恢复空间，也避免误删后难以追溯。

## 7. 预约容量一致性

### 7.1 创建预约

`createAppointment` 必须补充校验：

1. 用户必须有 `openid`。
2. 服务必须存在且 `isActive: true`。
3. 时段必须存在且 `isAvailable: true`。
4. `bookedCount < maxCount`。
5. 手机号、姓名、车型、日期、时段不能为空。
6. 创建预约成功后，同步增加时段 `bookedCount`。

如果微信云数据库事务能力可用，应使用事务完成“检查时段、创建预约、增加 bookedCount”。如果不使用事务，则至少在云函数中重新读取时段并做条件判断，降低并发超卖概率。

### 7.2 更新预约状态

`updateAppointment` 必须补充权限和容量同步：

- 普通用户只能取消自己的 `pending` 预约。
- 管理员可以确认、完成、取消任意预约。
- 状态值必须限定为 `pending`、`confirmed`、`completed`、`cancelled`。
- 从非 `cancelled` 变为 `cancelled` 时，回退对应时段 `bookedCount`，最低不小于 0。
- 从 `cancelled` 恢复为其他状态时，需要重新校验时段容量后再增加 `bookedCount`。

## 8. 接口调整

### 8.1 bindAdmin

入参：

```ts
{
  inviteCode: string
}
```

成功返回：

```ts
{
  isAdmin: true
}
```

失败返回：

```ts
{
  code: -1,
  message: "邀请码无效"
}
```

### 8.2 manageTimeSlot

新增 `updateWeekly`：

```ts
{
  action: 'updateWeekly',
  configs: WeeklyConfig[]
}
```

成功返回：

```ts
{
  generatedCount: number,
  updatedCount: number,
  closedCount: number
}
```

## 9. 错误处理

前端显示用户可理解的提示：

- 邀请码为空：`请输入邀请码`
- 邀请码无效：`邀请码无效`
- 邀请码过期：`邀请码已过期`
- 无管理员权限：`无管理员权限`
- 时段已约满：`该时段已约满，请选择其他时间`
- 保存每周配置失败：展示云函数返回 message

后端统一返回 `{ code, message, data }`，继续兼容现有 `callFunction` 封装。

## 10. 测试建议

### 10.1 邀请码

- 未输入邀请码时绑定失败。
- 错误邀请码绑定失败。
- 过期邀请码绑定失败。
- 超过使用次数的邀请码绑定失败。
- 有效邀请码绑定成功，并能看到管理后台入口。
- 已是管理员再次绑定，不重复消耗邀请码次数。

### 10.2 每周时段

- 保存周六启用规则后，未来 14 天内所有周六生成时段。
- 重复保存同一规则不会生成重复时段。
- 修改 `maxCount` 后已有时段更新容量。
- 停用某星期后，未来对应时段变为不可用。
- 已有预约的时段不会被删除。

### 10.3 预约容量

- 满员时段不能继续预约。
- 取消预约后 `bookedCount` 回退。
- 普通用户不能更新别人的预约。
- 非管理员不能确认或完成预约。
- 管理员可以确认、完成、取消预约。

## 11. 实施顺序

1. 修改 `bindAdmin`，实现邀请码校验和日志。
2. 在前端增加管理员邀请码输入入口。
3. 修改 `manageTimeSlot`，实现 `updateWeekly` 和未来 14 天生成逻辑。
4. 修改 `createAppointment`，补充服务、时段和容量校验。
5. 修改 `updateAppointment`，补充权限校验和容量同步。
6. 补充前端错误提示。
7. 运行构建或类型检查，并在微信开发者工具中验证核心流程。
