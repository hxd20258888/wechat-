# P0-P2 预约功能优化详细设计

更新时间：2026-07-24

本文档用于确认「车音工坊」本轮预约功能优化的详细设计。本文只做设计确认，不进入编码实现。

本次根据产品反馈做了三项关键修正：

- 预约必须绑定微信授权用户。未完善微信头像昵称的用户不能提交预约，否则用户退出后重新登录无法稳定查看自己名下的预约。
- 用户取消预约功能保留，暂时不设置时间限制。
- 设计按功能拆分，每个功能分别说明前端、后端、数据库、边界处理和验收标准，方便后续开发落地。

---

## 1. 总体原则

### 1.1 用户身份原则

预约记录必须属于一个已授权用户。

用户需要先完成微信头像昵称授权，系统在 `users` 集合中创建或更新用户记录，然后才允许提交预约。预约表单中的姓名和手机号只用于门店联系，不作为用户身份隔离依据。

### 1.2 审核可用性原则

预约功能不能因为未登录而表现为“不可用”。

未授权用户进入预约页时，不应直接被跳走到「我的」页，也不应只显示空白或禁用状态。页面应展示预约流程，并在合适位置引导用户完成授权。授权完成后继续当前预约流程。

### 1.3 数据一致性原则

预约创建、取消、确认、完成都必须保持预约状态和时段库存一致。

涉及 `appointments` 和 `time_slots` 的变更应优先使用事务或等价的防重复逻辑，避免重复提交、重复取消、超额预约。

### 1.4 增量兼容原则

新增字段必须兼容历史数据。

老预约、老服务、老用户没有新增字段时，页面应正常展示，不允许因为字段缺失导致页面崩溃。

## 2. 功能一：预约页授权引导与主流程可用性

### 2.1 目标

解决微信审核检测“预约功能无法使用”的风险，同时保证预约必须绑定微信授权用户。

### 2.2 用户流程

1. 用户进入「预约」tab。
2. 页面加载服务列表，允许用户选择服务。
3. 用户选择日期和时段。
4. 用户填写姓名、手机号、车型、备注。
5. 用户点击「确认预约」。
6. 如果用户未完成微信授权：
   - 页面弹出授权引导面板。
   - 用户选择微信头像并填写/确认昵称。
   - 系统调用 `login` 云函数创建或更新用户。
   - 授权成功后自动继续提交预约，或回到表单由用户再次确认。
7. 如果用户已授权，直接提交预约。
8. 提交成功后进入预约提交结果状态。

### 2.3 前端设计

涉及文件：

- `src/pages/booking/index.tsx`
- `src/pages/booking/index.module.scss`
- `src/hooks/useUser.ts`
- `src/services/cloud.ts`

页面状态：

- `servicesLoading`：服务加载中。
- `servicesError`：服务加载失败。
- `timeSlotsLoading`：时段加载中。
- `timeSlotsError`：时段加载失败。
- `authVisible`：授权引导面板是否展示。
- `authSubmitting`：授权提交中。
- `pendingSubmitAfterAuth`：授权成功后是否继续提交预约。
- `submitResult`：预约提交成功后的结果信息。

授权引导面板：

- 标题：`完成微信授权后提交预约`
- 说明：`用于保存和查看你的预约记录，姓名和手机号仅用于门店联系`
- 头像按钮：使用微信小程序 `openType="chooseAvatar"`
- 昵称输入：使用 `type="nickname"`
- 操作按钮：`完成授权并提交`、`暂不授权`

交互规则：

- 用户可在未授权状态下浏览服务、选择时间、填写表单。
- 用户点击「下一步」进入填写信息步骤前强制授权，授权通过后再进入下一步。
- 用户取消授权时停留在当前表单，不清空已填写内容。
- 授权成功后保存 `userInfo` 到本地缓存，并继续提交预约。
- 页面不再因为未登录自动 `switchTab` 到「我的」页。

### 2.4 后端设计

涉及云函数：

- `cloudfunctions/login/index.js`
- `cloudfunctions/createAppointment/index.js`

`login` 云函数：

- `mode: 'check'`：检查当前 openid 是否已有用户。
- `mode: 'create'`：创建新用户，要求昵称和头像。
- `mode: 'updateProfile'`：更新已有用户资料，要求昵称和头像。

`createAppointment` 云函数新增规则：

1. 获取 `OPENID`。
2. 查询 `users` 集合，确认当前 openid 对应用户存在。
3. 如果用户不存在，返回 `code: -2`，`message: '请先完成微信授权后再预约'`。
4. 用户存在后才继续校验服务、时段、表单字段。
5. 创建预约时写入 `_openid`、`userId`、`userSnapshot`。

`userSnapshot` 建议字段：

```json
{
  "nickname": "用户昵称",
  "avatar": "头像地址"
}
```

### 2.5 数据库设计

`users` 集合沿用现有字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| _openid | string | 微信用户唯一标识 |
| nickname | string | 微信昵称 |
| avatar | string | 微信头像 |
| phone | string | 用户手机号，可为空 |
| isAdmin | boolean | 是否管理员 |
| createTime | date | 创建时间 |
| updateTime | date | 更新时间 |

`appointments` 新增字段：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| userSnapshot | object | 否 | 提交时用户头像昵称快照 |

兼容规则：老预约没有 `userSnapshot` 时，详情页可以只显示客户姓名和手机号。

### 2.6 边界处理

- 用户拒绝授权：停留在预约表单，提示 `完成微信授权后才能提交预约`。
- 授权成功但预约提交失败：保留表单内容，展示云函数错误。
- 授权后用户马上退出小程序：本地缓存已保存，下次进入可识别登录状态。
- 本地缓存有用户但云端用户不存在：提交时云函数返回授权错误，前端清理本地缓存并重新引导授权。
- 用户更换微信号：openid 改变，看到的是新账号预约，不混用旧账号数据。

### 2.7 验收标准

- 未授权用户能进入预约页并操作到提交前。
- 未授权用户点击「下一步」进入填写信息步骤时出现授权引导，而不是被跳转离开。
- 授权成功后可以提交预约。
- 创建的预约能在该微信用户重新登录后查看。
- 不同微信用户不能互相看到预约。

## 3. 功能二：服务空状态优化

### 3.1 目标

避免审核人员或真实用户看到空服务列表后误判预约功能不可用。服务为空和接口失败必须区分。

### 3.2 用户流程

1. 用户进入首页或预约页。
2. 系统加载服务。
3. 如果有服务，展示服务列表。
4. 如果无服务，只展示明确提示和返回上一层按钮。
5. 如果加载失败，展示重试入口。

### 3.3 前端设计

涉及文件：

- `src/pages/home/index.tsx`
- `src/pages/booking/index.tsx`
- `src/pages/booking/index.module.scss`

首页空状态：文案 `暂无可预约服务，请稍后再试`，操作 `刷新`。

预约页服务空状态：文案 `暂无可预约服务，请稍后再试或联系门店`，操作仅保留 `返回上一层`。

加载失败状态：文案 `服务加载失败，请检查网络后重试`，操作 `重新加载`。

### 3.4 后端设计

涉及云函数：`getServices`。

后端保持现有查询逻辑：查询 `isActive: true` 的服务，按 `sortOrder` 升序返回。

### 3.5 数据库设计

`services` 审核期必须至少有一条 `isActive = true` 的服务。

建议审核期默认服务：基础听感调音、进阶系统调校、故障诊断。

### 3.6 边界处理

- 服务接口失败和服务为空必须区分。
- 服务为空时不允许用户进入后续预约步骤，也不展示下一步入口。
- 服务加载失败时不清空上一次已成功加载的数据，避免网络抖动造成页面突然空白。

### 3.7 验收标准

- 服务为空时页面有明确提示。
- 接口失败时用户知道可以重试。
- 有服务时首页和预约页都能正常展示。

## 4. 功能三：预约提交与成功结果

### 4.1 目标

让用户明确知道预约已经提交成功，但仍处于等待管理员确认状态。

### 4.2 用户流程

1. 用户完成授权。
2. 用户填写预约表单。
3. 点击「确认提交」。
4. 云函数创建 `pending` 预约。
5. 页面显示成功结果。
6. 用户可以查看我的预约、继续预约或返回首页。

### 4.3 前端设计

涉及文件：`src/pages/booking/index.tsx`、`src/pages/booking/index.module.scss`。

提交按钮文案：提交前 `确认提交`，提交中 `提交中...`。

成功结果区展示：

- 标题：`预约已提交`
- 副标题：`技师确认后，预约状态会更新为已确认`
- 预约编号、服务名称、服务价格、日期时段、联系人、手机号、车型、状态 `待确认`
- 操作按钮：`查看我的预约`、`继续预约`、`返回首页`

### 4.4 后端设计

涉及云函数：`createAppointment`。

返回数据建议扩展为：

```json
{
  "_id": "appointmentId",
  "status": "pending",
  "serviceName": "基础听感调音",
  "date": "2026-07-25",
  "timeSlot": "10:00-12:00"
}
```

前端不需要再次查询即可展示成功结果。

### 4.5 数据库设计

`appointments` 创建字段：`_openid`、`userId`、`userSnapshot`、`serviceId`、`serviceName`、`servicePrice`、`date`、`timeSlot`、`status`、`customerName`、`phone`、`carModel`、`remark`、`createTime`、`updateTime`。

### 4.6 边界处理

- 重复点击提交：前端 `submitting` 禁用；后端依靠时段容量事务兜底。
- 提交时服务下架：返回 `服务不存在或已下架`。
- 提交时时段关闭：返回 `该时段不可预约`。
- 提交时时段已满：返回 `该时段已约满，请选择其他时间`。
- 手机号格式错误：返回 `手机号格式不正确`。

### 4.7 验收标准

- 提交成功后不只显示 Toast。
- 用户能看到预约编号和待确认状态。
- 提交失败不会清空表单。
- 同一时段达到容量后不能继续创建预约。

## 5. 功能四：用户取消预约

### 5.1 目标

允许用户取消自己的预约，暂不设置取消时间限制。

### 5.2 用户流程

1. 用户进入「我的」页。
2. 用户查看预约列表。
3. 用户点击预约卡片进入详情，或直接在列表点击取消。
4. 用户点击「取消预约」。
5. 系统弹窗确认。
6. 用户确认后调用云函数取消。
7. 预约状态变为 `cancelled`，对应时段释放容量。

### 5.3 前端设计

涉及文件：`src/pages/mine/index.tsx`、`src/pages/appointmentDetail/index.tsx`。

展示规则：`pending` 和 `confirmed` 显示「取消预约」；`completed` 和 `cancelled` 不显示取消。

确认弹窗：标题 `取消预约`，内容 `确定要取消这个预约吗？取消后该时段会释放。`，确认按钮 `确认取消`。

取消成功后 Toast：`预约已取消`，并刷新预约列表或详情。

### 5.4 后端设计

涉及云函数：`updateAppointment`。

用户取消规则：当前 openid 必须是预约 `_openid`；目标状态必须是 `cancelled`；当前状态允许为 `pending` 或 `confirmed`；当前状态为 `completed` 或 `cancelled` 时拒绝或幂等返回。

管理员取消规则：管理员可取消 `pending` 和 `confirmed`；管理员不可取消 `completed`；重复取消 `cancelled` 推荐返回成功，避免重复点击误报。

时段释放：从非 `cancelled` 变为 `cancelled` 时，`time_slots.bookedCount - 1`，最低为 0。

### 5.5 数据库设计

`appointments` 更新字段：`status`、`cancelBy`、`cancelTime`、`updateTime`。

`time_slots` 更新字段：`bookedCount`、`updateTime`。

### 5.6 边界处理

- 用户取消别人的预约：返回 `无权限更新该预约`。
- 用户重复取消：不重复释放时段容量。
- 时段记录不存在：推荐保持严格，返回 `预约时段不存在`，由管理员处理。
- 两个端同时取消：事务内二次读取当前状态，确保只释放一次。

### 5.7 验收标准

- 用户能取消自己的待确认和已确认预约。
- 用户不能取消别人的预约。
- 已完成预约不能取消。
- 取消后时段容量恢复。
- 重复取消不会导致 `bookedCount` 变成负数。

## 6. 功能五：预约详情页

### 6.1 目标

让用户和管理员在一个页面查看完整预约信息，并按身份执行允许的操作。

### 6.2 用户流程

用户端：进入「我的」页，点击预约卡片，进入详情，查看服务、时间、联系人、车型和状态，并根据状态取消预约。

管理员端：进入预约管理，点击预约卡片，进入详情，查看完整信息，并确认、取消、完成预约。

### 6.3 前端设计

新增页面：

- `src/pages/appointmentDetail/index.tsx`
- `src/pages/appointmentDetail/index.module.scss`
- `src/pages/appointmentDetail/index.config.ts`

路由参数：`id` 为预约 ID，`from` 可选为 `mine` 或 `admin`。

页面区块：状态区、服务区、时间区、联系人区、车型区、操作区。

### 6.4 后端设计

新增云函数：`getAppointmentDetail`。

入参：`appointmentId`。

逻辑：获取当前 openid；查询 `users` 判断是否管理员；查询预约；普通用户只能访问 `_openid === openid` 的预约；管理员可访问所有预约；本轮不返回复查关联信息。

### 6.5 数据库设计

无需新增集合。建议 `appointments` 增加索引：`_openid`、`_openid + status`、`status + date`。

### 6.6 边界处理

- 预约不存在：显示 `预约不存在或已删除`。
- 无权限访问：显示 `无权限查看该预约`。
- 管理员权限本地缓存失效：以后端判断为准。
- 老预约缺少新增字段：对应区块隐藏或显示 `未填写`。

### 6.7 验收标准

- 用户只能查看自己的预约详情。
- 管理员可以查看全部预约详情。
- 不同状态展示不同操作。
- 老预约详情不崩溃。

## 7. 功能六：管理员预约状态流转

### 7.1 目标

规范管理员确认、取消、完成预约的状态流转，避免非法状态回退。

### 7.2 管理员流程

管理员进入预约管理，按状态筛选，点击预约进入详情，对 `pending` 执行确认或取消，对 `confirmed` 执行完成或取消，操作后刷新详情和列表。

### 7.3 前端设计

涉及文件：`src/pages/adminAppointments/index.tsx`、`src/pages/appointmentDetail/index.tsx`。

按钮规则：`pending` 显示确认预约、取消预约；`confirmed` 显示完成服务、取消预约；`completed` 和 `cancelled` 无状态按钮。

### 7.4 后端设计

涉及云函数：`updateAppointment`。

状态流转白名单：`pending -> confirmed`、`pending -> cancelled`、`confirmed -> completed`、`confirmed -> cancelled`。`completed` 和 `cancelled` 不允许再流转。

取消时释放时段；确认和完成不改变时段容量。

### 7.5 数据库设计

`appointments` 增加操作记录字段：`confirmedTime`、`completedTime`、`cancelTime`、`operatorOpenid`。

当前阶段不新增操作日志集合；后续需要完整审计时再新增 `appointment_logs`。

### 7.6 边界处理

- 已完成预约不能取消或改回确认。
- 已取消预约不能恢复。
- 管理员重复点击确认：如果已是 `confirmed`，推荐返回成功。
- 管理员和用户同时操作：以后端事务中读取的当前状态为准。

### 7.7 验收标准

- 管理员能完成允许的状态操作。
- 非法状态流转被后端拒绝。
- 状态变化后用户端可见。
- 取消后时段容量正确释放。

## 8. 功能七：预约时间可用性优化

### 8.1 目标

预约页只展示管理员已经维护过、开放、且仍有容量的可预约日期和时段，避免展示大量无意义日期。本轮不新增批量生成时段能力，只消费管理员现有维护结果。

### 8.2 用户流程

1. 用户进入预约页并选择服务。
2. 系统查询未来可预约日期，而不是固定展示未来 14 天。
3. 页面只展示存在可用时段的日期。
4. 用户选择某个日期。
5. 系统展示该日期下未约满且开放的时段。
6. 如果未来没有任何可预约日期，展示明确提示。

### 8.3 前端设计

涉及文件：

- `src/pages/booking/index.tsx`
- `src/pages/booking/index.module.scss`

预约页日期展示规则：

- 不再用固定未来 14 天日期作为最终展示列表。
- 页面加载或服务选择后调用可预约日期接口。
- 日期横向列表只展示有开放且未约满时段的日期。
- 每个日期可显示：月日、星期、剩余时段数。
- 选择日期后再加载该日期具体时段。

预约页空状态：

- 无可预约日期：`暂无可预约时间，请稍后再试或联系门店`
- 某日期时段刚好被约满：`该日期暂无可预约时段，请选择其他日期`
- 时段加载失败：`时段加载失败，请稍后重试`

管理员端说明：

- 本轮不新增批量生成时段。
- 管理员继续通过现有时段管理能力维护日期和时段。
- 用户端只展示管理员已维护出的有效日期和有效时段。

### 8.4 后端设计

涉及云函数：`getTimeSlots`。

新增或扩展 `getTimeSlots` 查询模式：

- `mode: 'availableDates'`：返回未来可预约日期列表。
- `mode: 'slotsByDate'` 或默认传 `date`：返回指定日期时段。

`availableDates` 入参建议：

```json
{
  "mode": "availableDates",
  "startDate": "2026-07-25",
  "endDate": "2026-08-24"
}
```

`availableDates` 返回建议：

```json
[
  { "date": "2026-07-25", "availableCount": 2 },
  { "date": "2026-07-26", "availableCount": 1 }
]
```

`availableDates` 查询规则：

- 只统计管理员已经维护过的 `time_slots` 数据。
- 只统计 `isAvailable = true` 的时段。
- 只统计 `bookedCount < maxCount` 的时段。
- 只返回 `availableCount > 0` 的日期。
- 默认查询未来 31 天内的数据；如果未来 31 天都没有维护时段，则返回空数组。

指定日期时段查询规则：

- 只返回 `isAvailable = true` 的时段。
- 只返回 `bookedCount < maxCount` 的时段。
- 按 `startTime` 升序排列。

### 8.5 数据库设计

沿用 `time_slots` 集合：

| 字段 | 类型 | 说明 |
|------|------|------|
| slotKey | string | 唯一业务键：日期_开始_结束 |
| date | string | 日期 |
| startTime | string | 开始时间 |
| endTime | string | 结束时间 |
| maxCount | number | 最大预约数 |
| bookedCount | number | 已预约数 |
| isAvailable | boolean | 是否开放 |
| createTime | date | 创建时间 |
| updateTime | date | 更新时间 |

索引建议：

- `date + isAvailable`
- `slotKey`

### 8.6 边界处理

- 未来 31 天没有任何可预约时段：预约页显示无可预约时间，不展示无效日期。
- 用户已选择日期后，该日期最后一个时段被别人预约：提交失败后清空已选时段并刷新可预约日期。
- 日期列表加载成功后，时段加载失败：保留日期选择，展示时段重试入口。
- 管理员关闭某时段后，用户端刷新后不再展示该时段。
- 管理员维护了日期但所有时段已满，该日期不展示。

### 8.7 验收标准

- 预约页只展示管理员维护过且有可约时段的日期。
- 没有可约日期时不会展示一排无意义日期。
- 用户选择日期后只看到开放且未约满的时段。
- 管理员关闭或约满的日期/时段不会继续展示给用户。

### 11.1 自动化测试

建议覆盖：

- 未授权用户不能提交预约。
- 授权用户可以提交预约。

### 11.2 手工验收

预约授权：清空本地用户缓存，进入预约页，选择服务和时段，点击「下一步」进入填写信息步骤时完成微信授权，填写表单并提交，预约提交成功，退出后重新登录能看到自己的预约。

用户取消：创建待确认预约并取消，检查时段容量恢复；创建已确认预约并取消；已完成预约不显示取消按钮。

管理员：确认待确认预约，完成已确认预约，取消待确认或已确认预约，非法状态操作被拒绝。

## 12. 已确认产品决策

1. 授权引导在用户点击「下一步」进入填写信息步骤时弹出，不在进入预约页时弹出。
2. 授权成功后自动进入填写信息步骤，不自动提交预约；用户仍需确认表单后点击提交。
3. 用户可以取消自己的待确认和已确认预约，暂不设置时间限制。
4. 用户取消已确认预约暂不考虑管理员提醒，后续通知能力放到 P3。
5. 服务为空时只展示明确提示和「返回上一层」，不提供下一步入口。
6. 预约页只展示管理员维护过、开放、未约满的日期和时段，不展示无效日期。
7. 本轮暂不做批量生成时段能力，只消费管理员现有维护结果。
8. 本轮暂不做车辆档案、调音需求、服务套餐、复查预约、管理员内部备注和客户标签。
9. 绑定管理员应要求当前用户已完成微信授权并存在于 `users` 集合；不建议在 `bindAdmin` 中创建空昵称/空头像管理员用户。
